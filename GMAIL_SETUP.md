# Activate real Gmail and live AI

You can connect Gmail and Outlook at the same time under your application account. Outlook uses a separate Microsoft registration; see [OUTLOOK_SETUP.md](OUTLOOK_SETUP.md).

The application includes Google OAuth connection, private Gmail imports, live AI processing through the existing OpenAI provider, and explicitly approved Gmail delivery. **Live verification requires your Google OAuth client credentials, an OpenAI key/model, and your manual Google consent.** None of those credentials are supplied by the project. The working offline demo remains available while you configure them.

## 1. Prepare the private configuration

Run from the project root:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt -c requirements.lock.txt
.\.venv\Scripts\python.exe -m scripts.configure_gmail
```

The script generates `TOKEN_ENCRYPTION_KEY` in ignored `.env`, preserves existing credentials, and writes a private checklist under `artifacts/gmail-setup-checklist.txt`. Back up the encryption key privately: losing or changing it makes saved Gmail credentials unreadable. It is not uploaded to GitHub.

## 2. Create your Google OAuth client

1. Open [Google Cloud Console](https://console.cloud.google.com/) and select or create a project.
2. [Enable Gmail API](https://console.cloud.google.com/apis/library/gmail.googleapis.com) for that project.
3. Configure [Google Auth Platform branding](https://console.cloud.google.com/auth/branding): application name, support email and developer contact.
4. Under [Audience](https://console.cloud.google.com/auth/audience), use **External → Testing** for your personal trial and add your Gmail address as a test user. Google Workspace organizations can use an appropriate internal setup.
5. Under [Data Access](https://console.cloud.google.com/auth/scopes), configure `https://www.googleapis.com/auth/gmail.readonly` and `https://www.googleapis.com/auth/gmail.send`. The app does not request deletion, label modification or permission to mark messages as read.
6. Under [Clients](https://console.cloud.google.com/auth/clients), create an OAuth client of type **Web application**.
7. Add the **exact** authorized redirect URI printed in `artifacts/gmail-setup-checklist.txt` (including the trailing slash). For local development it can be `http://127.0.0.1:8501/`; for the public dashboard use its exact HTTPS root URL. Google returns to Streamlit; you do not expose the private FastAPI port.
8. Copy the client ID and client secret into `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` in the private `.env`. Set `GOOGLE_REDIRECT_URI` to that exact same URI.

Official guides: [Google's Python quickstart](https://developers.google.com/workspace/gmail/api/quickstart/python), [web-server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server), and [Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes). Testing is intended for your listed test users. A broadly available public Gmail integration needs Google's applicable consent/verification process; do not assume testing mode provides unrestricted public Gmail access. Temporary tunnel hostnames can change and then require updating both the Google client and `.env`; use a stable HTTPS domain for ongoing operation.

## 3. Configure live OpenAI

Create an API key in your own [OpenAI API account](https://platform.openai.com/api-keys), then privately configure:

```dotenv
OPENAI_API_KEY=your-private-key
OPENAI_MODEL=an-account-supported-model-with-responses-tools-and-structured-outputs
LLM_PROVIDER=openai
```

The model must support Responses, tool calling and structured output parsing. No model is hardcoded. API requests use your account and can incur charges. Do not paste the key into chat or commit `.env`. Processing a Gmail message sends its text and relevant same-owner thread context to your configured OpenAI service; only process messages you are authorized to share with that service.

Restart after environment changes:

```powershell
docker compose up --build -d
```

For non-Docker development apply `alembic upgrade head` and restart your Python services. Gmail messages cannot be processed with the offline rule provider. Shared fictional demo emails still support the existing demo workflow.

## 4. Connect and use Gmail

1. Sign in to your own application account and open **Gmail**.
2. Click **Connect my Gmail**, then **Continue to Google consent**. You choose the Gmail account and review permissions yourself. Never give this application your Gmail password.
3. Google redirects back to the dashboard. OAuth state is single-use, expires after ten minutes, and uses PKCE. If asked, sign in again with the same application account that initiated connection; the callback requires that identity before linking your Gmail. A link generated by another user's account cannot attach your Gmail to that account while you are signed in as yourself.
4. Open **Gmail → Sync latest 20 Gmail messages**. This imports recent Inbox messages without marking them read or modifying their Gmail labels. Existing imports are deduplicated. Large/malformed messages are skipped; attachments are not executed or extracted.
5. Open **Inbox**, select a private Gmail message, and process it with live AI. Review extracted facts, summary, evidence and draft. Fictional seeded business records are excluded from real-mail tool lookups; absent real business data produces clarification rather than invented status.
6. Save any draft edits, then **Approve** the current revision. Editing resets approval.

Imports are private to the connecting application user, including from other Admin accounts and the shared service integration token. Manual text-entry/demo emails remain shared; **do not paste confidential email into the shared demo input**. This is per-message mailbox privacy inside a single business workspace, not full organizational multi-tenancy.

## 5. Enable actual sending deliberately

Once connection and live AI work, set `GMAIL_SEND_ENABLED=true` in `.env` and restart the API. In **Reply Review**, verify the displayed reply recipient and approved draft, tick the explicit confirmation, then click **Send approved reply via Gmail**. The request checks mailbox ownership, Reviewer/Admin role, current revision, approval, recipient and confirmation. Shared demo drafts cannot be sent.

Only a Gmail API response containing a message ID produces a `sent` status. Duplicate send requests do not send again. A timeout, interrupted attempt or unconfirmed response locks delivery; check **Gmail Sent** manually before any recovery. There are no automatic delivery retries. Drafts with a delivery attempt cannot be edited/re-approved or reused for another send.

Official [Gmail sending guide](https://developers.google.com/workspace/gmail/api/guides/sending). This integration sends one reply to the confirmed sender/Reply-To address; it does not implement Reply All, attachments or campaigns.

## Limits and verification

- Sync is user-triggered and imports the latest 20 Inbox messages per run; it is not continuous background monitoring or a complete historical mailbox migration.
- Google access/refresh credentials and PKCE verifiers are encrypted using Fernet before database storage. Token refresh is handled by Google's client libraries; updated credentials are saved encrypted after successful operations.
- Disconnect revokes the Google grant and removes saved connection credentials; imported messages stay private in the app. Tokens can also be revoked from your Google account's third-party access settings.
- API, OAuth, privacy and delivery tests mock Google and OpenAI. They never send real email or spend API credits. Live OAuth and actual delivery remain unverified until you configure credentials and complete consent.
- Production operation additionally needs an always-on host, stable domain, appropriate Google verification, backups/key retention, monitoring and the privacy controls required for your organization. A temporary tunnel on a sleeping computer does not provide unattended uptime.
